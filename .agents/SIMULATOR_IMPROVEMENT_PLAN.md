# FlightSimulator — аналіз і довгостроковий план покращення

Дата: 2026-07-06. Мета симулятора: генерувати тестові відео місцевості + файл калібрації, які система Topometric Localization споживає **без жодних ручних маніпуляцій**.

---

## ✅ ЩО ВИПРАВЛЕНО СЬОГОДНІ (CalibrationLogger + wiring)

Три вади, через які якорі не відповідали відео DatabaseBuilder:

| Було | Стало |
|------|-------|
| Якір з довільного кадру F отримував `frame_id = F//frame_step` — але слот S містить кадр `S*frame_step`, тож матриця могла належати кадру, зміщеному до 29 кадрів (~145 м при 150 м/с) | Якір створюється **лише на кадрах, кратних frame_step** — матриця відповідає точно тому кадру, який DatabaseBuilder кладе у слот. Лічильник кадрів у main.py ведеться в локстепі з VideoWriterSink |
| 1 точка (центр кадру) | **5 точок** (центр + 4 на 20%/80% кадру), GPS кожної — точною проєкцією H1; LSQ-фіт по всіх 5 + чесні RMSE/median/max (видно нелінійність гомографії) |
| Якір писався при зміні waypoint — **точно на початку розвороту** survey-патерну | Якір ставиться лише при **стабільному курсі**: |Δyaw| у ковзному вікні < 1.5° (конфіг), + мінімальний інтервал між якорями у слотах |
| `projection: {"type": ...}` — система читає ключ `"mode"` (працювало випадково через fallback) | Формат v2.3: `"mode": "WEB_MERCATOR"` + `frame_size` + атомарний запис |
| det матриці не перевірявся | Санітарна перевірка det<0 (px Y↓ → mercator Y↑), самодіагностика в notes |

Нові CLI-параметри: `--anchor-spacing-slots` (дефолт 15), `--anchor-yaw-stability-deg` (дефолт 1.5). **Критично: `--frame-step` мусить збігатися з `database.frame_step` системи локалізації (обидва дефолти 30).**

Верифіковано крос-проєктним тестом: згенерований файл завантажується `MultiAnchorCalibration` (v2.3), якорі лише на прямих ділянках, на межах слотів, позиції центру збігаються з GT, інтерполяція між якорями зберігає det<0.

## Робочий цикл «нуль маніпуляцій» (як є зараз)

```
python -m simulator.main --mode record --video-file flight.mp4 --calib-file calibration.json --frame-step 30
→ DroneLocalization: створити місію з flight.mp4 (той самий frame_step)
→ Завантажити калібрування calibration.json → Запустити пропагацію
```

Залишкові ручні кроки: вибір відео в діалозі місії + кнопка завантаження калібрування + кнопка пропагації. Як їх прибрати — Етап 1 нижче.

## ЕТАП 1 — Повна автоматизація зв'язки (1–2 дні)

### 1.1 Експорт готової структури проєкту
Симулятор пише не два файли, а **готову папку проєкту** DroneLocalization:

```
output_dir/
├── project.json          # ProjectSettings: source з video_file, calibration_file,
│                         # altitude_m, focal/sensor з CameraConfig (він і так
│                         # синхронізований із GSDCalculator)
├── flight.mp4
└── calibration.json
```

Користувач у DroneLocalization натискає «Відкрити проєкт» — і все. Потрібно: невеликий `project_exporter.py` (~80 рядків), формат читається з `src/core/project.py`.

### 1.2 Ground-truth сайдкар для бенчмарка
`ground_truth.json`: для КОЖНОГО кадру відео — GT-афінна матриця (та сама лінеаризація H1, що для якорів) + GPS центру. Це:
- еталон для `benchmark_propagation.py` (Етап 0.1 плану покращення pose graph) — міряємо похибку пропагації у метрах по всіх кадрах;
- основа для майбутнього режиму «GT-калібрування без пропагації».
Вартість: ~30 рядків у CalibrationLogger (він уже все обчислює).

### 1.3 Метадані сумісності
У `calibration.json` додати блок `"generator": {"tool": "FlightSimulator", "frame_step": 30, "fps": 30, "video_file": "flight.mp4", "gt_file": "ground_truth.json"}` — система локалізації зможе валідувати збіг frame_step із БД і попереджати ДО пропагації.

### 1.4 Кодек відео
`mp4v` → **H.264 через PyAV/imageio-ffmpeg** (або `avc1` де доступний OpenH264): менші файли, кращa сумісність із decord (який використовує DatabaseBuilder), відтворюваність у будь-якому плеєрі. CRF-конфіг для контролю якості (тестувати локалізацію на різних рівнях компресії — теж корисний експеримент).

## ЕТАП 2 — Реалістичність відео (1–2 тижні, по одному ефекту)

Зараз рендер — «ідеальна» ортокарта: без шуму, без освітлення, без динаміки. Локалізація на такому відео завжди «занадто успішна». Ефекти, кожен за конфіг-прапорцем (усі — numpy/OpenCV, без нових важких залежностей):

### Фотометрія (найбільший вплив на DINOv3/ALIKED)
1. **Сезонні/часові LUT** — 3–4 колірні пресети (літо/осінь/зима/вечір) + gamma/білий баланс. Ключовий тест: БД з «літа», локалізація на «осені».
2. **Тіні хмар** — Perlin-noise маска, що повзе по місцевості (шумить глобальні дескриптори, як у реальності).
3. **Сенсорний шум** — Gaussian/Poisson за ISO-моделлю + віньєтування + легкий JPEG-артефакт.
4. **Серпанок/димка** — Koschmieder: `I = I0·t + A·(1−t)`, t від псевдо-глибини.
5. **Motion blur** — спрямований kernel за швидкістю/yaw rate (реальний ворог ALIKED на швидких прольотах).

### Геометрія
6. **Гімбал-джиттер** — Perlin-шум малих кутів у камеру (зараз камера «прибита» до дрона).
7. **Дисторсія лінзи** — Brown-Conrady k1,k2 (перевіряє стійкість гомографії).
8. **Паралакс від рельєфу** — elevation-тайли ВЖЕ завантажуються (`download_elevation`), але площина рендера пласка. Displacement по DEM дасть чесний паралакс — головне джерело помилок афінної моделі в горбистій місцевості.
9. **Похилі ракурси** — pitch камери 10–30° (зараз надір) — тест перспективних гомографій.

### Динаміка (тест YOLO-маскування)
10. **Рухомі об'єкти** — спрайти авто по «дорогах» (просто прямі траєкторії): перевіряє, що маскування динаміки в DatabaseBuilder реально працює.

## ЕТАП 3 — Датасет-фабрика (паралельно з Етапом 2)

### 3.1 Сценарії як YAML
`scenarios/hilly_autumn_fast.yaml`: bbox, zoom, висота, швидкість, патерн, сет ефектів, seed. Запуск: `python -m simulator.batch scenarios/*.yaml --out datasets/`. Повна відтворюваність (фіксований seed для всіх шумів).

### 3.2 Еталонний сьют для регресії локалізації
3–5 сценаріїв (пряма траса / повернення-loop / hover / рельєф / крос-сезон) → нічний прогін `benchmark_propagation.py` + локалізації по GT. Це та сама захисна сітка з POSE_GRAPH_IMPROVEMENT_PLAN (Етап 0) — **одна інвестиція закриває обидва проєкти**.

### 3.3 Маніфест датасету
`manifest.json` на кожен датасет: сцена, параметри, хеші файлів, версія симулятора — щоб результати бенчмарків були порівнюваними в часі.

## ЕТАП 4 — Технології (за потребою, кожна — окреме рішення)

| Технологія | Навіщо | Коли варто |
|-----------|--------|-----------|
| **PyAV / imageio-ffmpeg** | H.264/H.265, контроль CRF, метадані | Етап 1.4 — одразу |
| **moderngl (OpenGL)** | Рендер з DEM-паралаксом і дисторсією на GPU; зараз warpPerspective на CPU обмежує роздільність/швидкість | Коли Етап 2.8 упреться в CPU |
| **opensimplex/noise** | Perlin для хмар/джиттера | Етап 2.2/2.6 |
| **pydantic для SimulatorConfig** | Той самий підхід, що в DroneLocalization: валідація, save/load YAML-сценаріїв | Етап 3.1 |
| **MAVLink-вихід (pymavlink)** | Телеметрія у стандартному форматі → тестування headless-режиму локалізації як з реальним дроном (RTSP+MAVLink) | Коли з'явиться інтеграція телеметрії в локалізацію |
| **RTSP-стрімінг (mediamtx + ffmpeg)** | Симулятор як live-джерело: end-to-end тест реального часу, а не файлів | Після Етапу 3 |
| Gazebo/AirSim/Flightmare | НЕ рекомендую: важкі, фотореалізм не потрібен (потрібна геоприв'язана ортокарта), поточний підхід точніший для цієї задачі | — |
